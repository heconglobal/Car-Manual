## Historical overview / eviction implementation

The browser first loads the catalogue, navigation and a prebuilt exterior/cabin overview. Engine, transmission, brake, fuel, wiring and other detailed explorers are fetched and constructed when selected. Catalogue search does not require their geometry to be resident.

The overview uses the existing authored body, cabin and lamp curves. Smooth surfaces have fewer samples; small cross-section breakpoints and the original part identities remain. Hidden mechanical interiors are omitted. Its typed geometry is generated at build time, compressed with gzip, and requested as one content-addressed local asset. Position coordinates in this overview use 16-bit quantization within each mesh's own bounds, and normals/ordinary UVs use normalized 16-bit attributes. Attribute components then use lossless, width-wrapped delta encoding and byte-plane grouping before gzip; decoding restores the exact compact bit patterns. Detailed explorers and the full mechanical audit retain their original source precision and construction. Overview quantization is a delivery optimization, not a claim of measured vehicle accuracy.

`npm run build` regenerates the overview when its model inputs change. `node scripts/build-overview.mjs` refreshes it during development. Previous descriptors and content-addressed assets are preserved. Source evidence includes the active payload's bytes; production evidence also hashes public assets. The browser checks the payload length and, in a secure context, its SHA-256 before decoding. Browsers without native gzip-stream support can use the procedural overview fallback.

The viewer retains the overview plus at most one detailed inspection family or vehicle-system allocation. Changing families or returning to the overview disposes the old geometries, materials, textures and renderer render-list references. A request that finishes after navigation cannot create or install its stale model. Search labels are created only when actually shown and removed when changing models. JavaScript module code remains in the browser's module cache, which is distinct from retaining full geometry and GPU resources.

Selecting a system requests its native contextual geometry. An explicit whole-vehicle cutaway or exploded view requests the complete vehicle; this mode costs more memory by design and is released when returning to the overview. The loading status stays visible during a requested load, queues framing/selection commands for the correct model, and offers a fresh reload if a module fails. Large first-time detailed assemblies can still take time to construct on a slow device; they no longer delay the first car view.

The generated overview currently contains 992,700 triangles in 948 meshes and transfers as a 4,845,709-byte compressed asset (26,026,732 bytes before transport decoding). Those figures describe the artifact, not a promised download time; connection and rendering performance still matter. Only the active content-addressed asset is requested. Older generated assets remain preserved locally.

At mobile drawer widths (up to 960px, including landscape phones and tablets), the perspective toolbar is hidden. Assembly access, reset and a 44-pixel View tools control remain available; body visibility, labels, wireframe and full-screen controls are in its disclosure. Search, component details, guides and Back to vehicle remain available. The title, return action and controls flow vertically when titles wrap, and whole-vehicle camera framing and fog distances compensate for portrait aspect ratios. Short landscape viewports use a compact header and controls, with the inspector scrolling internally so the car canvas fits the viewport.

Verification uses codec round-trip/error-bound checks, disposal/shared-resource tests, superseded-request tests, and browser cases for cold start, module deferral, cache eviction, navigation races, phone layouts and measured heap/render allocations. Timing reports identify the actual renderer and host. A narrow phone viewport on desktop Chromium is not a physical-phone speed measurement. Geometry byte counts are buffer allocations, not total process RAM; JavaScript heap and renderer allocation counts are reported separately.

## Next stage: detailed-assembly delivery

This feasibility review led to the Body/Engine delivery integration described above. Scope partitioning and workers remain unimplemented options. Under the previous eviction design, body-detail navigation took 47.9 seconds, of which 44.4 seconds was recorded as the detail load. The load interval includes module import and synchronous construction; the aggregate report does not separate those two costs. Its longest main-thread task was 44.0 seconds. Changing the loading message cannot remove that work.

The first implementation uses **full-precision, prebuilt Body and Engine family payloads**, downloaded during startup and decoded when first opened. `createBodyDetail()` already returns the same `{root, groups}` structure as the overview decoder, with direct mesh children and identity group transforms after `correctLegacyHandedness()`. `createEngineDetail()` has the same final structure; the generator now validates exact native bytes, metadata and every part bound for both families. Neither constructor returns a model-specific configuration or pose callback. Detail visibility, options, paint, selection and exploded offsets are applied by the viewer and catalogue. Therefore these two families do not require reconstruction of a hidden constructor closure after decoding.

The existing codec can preserve their buffers without overview quantization by using `encodeModel(model, {compact:false})`. Its current `compact` option couples quantization and byte packing; full-precision use must leave that option off, or first separate lossless packing from quantization. The payload must preserve every part and section ID, `spread` and `assemblySpread` vectors, `US-LHD` marker, mesh option/value flags, `materialName`, original color/emissive/opacity metadata, material properties, texture recipes and reflected label UV settings. The catalogue supplies nested section membership; the scene graph itself is flat. Export must occur immediately after the native constructor, before viewer-created ghost/wire materials or configuration mutations. The decoder must not apply the handedness conversion a second time.

Before enabling that payload, compare every native/decoded typed attribute and index byte, material and texture recipe, group ID, transform, bounds and explosion offset. Explicitly reject unsupported nested transforms, material arrays or material types instead of silently dropping them; the current codec assumes direct mesh children and standard/physical materials. Exercise body paint, both window/lock alternatives, scope navigation, isolation, return and disposal in the browser. Reuse the current content hash, payload integrity and distribution allowlist mechanisms. Measure the actual compressed size, decode time, first draw and peak retained buffers before deciding whether the full-family artifact is an acceptable network/RAM tradeoff. Generated payload sizes are recorded above. Browser decode, first-draw, peak-memory and navigation timings still require the current integrated probe.

For this first step, the asynchronous loader can fetch and verify bytes before returning a synchronous decoding builder, retaining the current request-cancellation check before allocation. If decoding or allocation instead becomes asynchronous, `createLatestModelRequest()` must explicitly await it and dispose a result that becomes obsolete before publication; its present allocator contract is synchronous. The restored viewer keeps the full vehicle and visited detail models in a persistent session cache, as requested by the owner. Compressed staging buffers are released after installation; decoded backing buffers remain owned by the model geometry. This is a deliberate change from the prior one-family eviction policy.

Smaller scope payloads are a later refinement. The exporter can group native part records by the catalogue's `inDetailSection()` membership and ship only the requested door, window mechanism or engine service scope. That avoids allocating the entire body family for one hinge pin. It also requires changing the family-only request key, resolving parent scopes that include descendants, preserving shared part identities across scopes, and checking guide transitions and geometry lookups. Filtering groups after constructing the whole family in the browser would not remove the measured constructor cost.

A worker is another option if generated downloads prove too large. Geometry builders are mostly transferable-buffer work, but `materials.js` uses `document.createElement('canvas')`; the worker path needs a recipe-only material adapter or equivalent `OffscreenCanvas` support. Transfer buffers rather than copying complete Three.js object graphs, recreate materials on the render thread, and use request tokens/worker cancellation to discard superseded work. Worker construction can protect UI responsiveness, but does not by itself reduce total CPU work, geometry memory, GPU uploads or shader time. Prebuilding the body family is the narrower first step; scope partitioning or workers should follow only if its measurements justify them.

Initial startup also needs a separate rendering profile if a firm speed budget is required. The final report contains 92 localhost resources and no font request or external origin. Readiness is set after the first `composer.render()`, after the document load event. The overview-load timer excludes WebGL renderer creation, the initial RoomEnvironment/PMREM work, and first shader compilation/draw; local HDR processing can also occur during initialization. Existing aggregate timings do not identify which of those accounts for the remaining startup time. Add phase timings before choosing a rendering change rather than attributing the 37.3-second run to network download alone.
