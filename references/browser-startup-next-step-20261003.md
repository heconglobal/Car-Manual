# Narrow startup follow-up proposal

**Recommendation: evaluate a worker for the existing Body surfaces stage only. Keep the restored complete-vehicle startup and persistent explorer cache as the default until an isolated browser comparison supports a change.** This document records source inspection; no worker, new startup asset, builder run or browser experiment was added.

Evidence: the [restored-loading probe](../artifacts/test-runs/2026-10-02T23-46-05.069Z-5f150345/results/performance-desktop-and-mo-ffdf9-ured-with-renderer-identity/performance/report.json) on source `1c101c22…` measured 68.76 s readiness, 62.66 s workshop preparation and a 21.44 s longest main-thread task. Consecutive stage-start markers give approximate intervals: Body surfaces **21.47 s**, exterior/cabin lighting **15.03 s**, engine/ignition **4.35 s**. These intervals also contain the following progress yield; they are not separately instrumented constructor durations. The final optimize/handedness work and download wait are not individually timed. The reviewed current build is source `5c3542bff03f1097c7aa7ba4e896c99021447c5fe30d0c96b3b060a185b4224c`, app `30ea1fb41f68e2475083f6b64755b0e6c666df818a0121c19a36e80c8d9f5d86`; the older timing run does not measure its later door/mobile changes.

## Smallest controlled experiment

Add an optional override for the single `Body surfaces` stage in `createVehicleTiered()`; leave synchronous `createVehicle()` as the authoritative audit path. A module worker would call the same `buildBody()` with fresh legacy-frame vehicle-owner groups and the same base materials. Return that stage's geometry to the main thread, attach it to the existing owner groups, then continue all remaining stages and native `finish()` before readiness. Do not move the entire viewer, configuration logic or sixteen explorers into workers.

The boundary has specific constraints:

- `buildBody()` already applies `bodyPoint` via `geometryTools.mapAdded()`. Return that result **before** `correctLegacyHandedness()`. Keep native final optimization and the one global handedness conversion on the main thread; do not pre-optimize the worker result if that changes merge order. The vehicle group spreads, owner systems and `configure`/`getConfiguration` closure remain in `model.js`.
- Transfer full-precision positions, normals, UVs, indices, geometry groups/draw ranges, mesh transforms, owner IDs, option/value/finish flags, `materialName`, original color/emissive/opacity metadata and material properties. The existing `encodeModel({compact:false})`/decoder is a candidate transport, with its flat-root/direct-mesh restrictions retained. Measure its copying, parsing and bounds-computation costs; do not presume these are free.
- `materials.js` currently calls `document.createElement('canvas')` for grain and text. Introduce an explicit recipe-only material/texture adapter for worker construction, rather than a production fake `document`. Recreate textures on the main thread from existing recipes with repeat/offset, color space and filtering settings preserved. Keep original text/UV handedness correction in the final native conversion. Geometry must never depend on placeholder texture pixels.
- Transfer ownership of the encoded `ArrayBuffer`, rather than structured-cloning Three.js objects or copying every buffer twice. Terminate the worker after delivery or cancellation. Main-thread decoded buffers then belong to the vehicle. Existing final optimization/reflection still creates temporary copies, so a worker is **not** a promised RAM reduction. Late results must not attach after the viewer closes; failures must remain visible, with the current native startup available when the optional worker path is unsupported.

This removes only the candidate body-construction pause from the UI thread. Lighting remains a roughly 15 s candidate pause in the measured run; shader/GPU draw cost also remains. Test the Body boundary before considering the identical stage mechanism for lighting. No additional 111 MB vehicle download is proposed.

## Why not directly substitute the detail models first?

Body reuse is plausible because its already-prefetched asset contains `bd-skin-*` groups mapped by `bodySurfaceOwners`. It is not a drop-in replacement: `bodyMaterials()` changes five material variants' bump/roughness values, the detail constructor discards owners outside that list, and the asset is already in final US-LHD coordinates. Coverage must first match every mesh produced by the native Body stage. Attaching after global reflection avoids converting it twice, but also changes final merge batching. Clones must have independent mutable material/original metadata; moving meshes out of the persistent explorer, or sharing mutable material state, would break navigation/configuration. Geometry could only be shared after all placement/reflection/optimization mutations finish.

Engine reuse has a clear `engineVehicleOwner()` mapping, including ignition/electrical owners and deliberate alternator/flywheel/exhaust/internal exclusions. Its prebuilt geometry is also already reflected. Installed placement must therefore be `R × enginePlacement × R` applied to the reflected detail coordinates, where `R=scale(-1,1,1)`, without another reflection/label-UV flip. Preserve `detailPartId`, all exclusions and the native configuration closure. Sharing geometry with a mesh placement avoids baking copies, but changes floating-point operation order and requires world-space comparison. Its measured native stage is much smaller than Body's. Neither reuse path is authorized as an unverified replacement by the existing native-detail round-trip checks alone.

## Promotion criteria

Compare the proposed Body result with the native stage and final vehicle: exact typed values/order where unchanged, every owner and option variant, material/texture recipes, all bounds, winding, labels and one LHD conversion. Run existing configuration, electrical visibility, headlamp, door, guide, explode/return and mobile framing checks; opening/revisiting cached explorers must retain their current build counts. Measure stage start/end, event-loop responsiveness during Body construction, longest main-thread tasks, complete readiness, transferred bytes and peak main/worker/process allocations on an otherwise idle host. Test cancellation/failure and a real target phone before claiming phone improvement. Keep the current restored loader unless those results show a practical benefit without missing geometry, appearance regressions or unacceptable peak memory.
